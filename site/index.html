Did your change break this,
or was it already broken?

Instant post-deploy blame attribution for Kubernetes. Takes a snapshot before your change, diffs live cluster state after, and isolates true regressions from background noise.

pipx install wasitme
wasitme demo --scenario crashloop 
$ wasitme diff --wait 15s

The Three Attribution Buckets

🔴

Broke After Your Change

New pod crashloops, image pull failures, surge in restart counts (≥ 3), or degraded HTTP endpoints. Fails CI with exit code 1.

🟡

Already Broken

Pre-existing failures present before you touched the cluster that did not worsen. Eliminates post-deploy blame and false alarms.

🟢

Fixed

Baseline issues that your deployment successfully resolved. Gives clear proof that your bugfix achieved its goal.

How wasitme Differs

Capability wasitme kubectl-snapshot Prometheus / Datadog
Primary Purpose Deploy Blame Attribution Forensics state dump Continuous metric monitoring
Rolling Update Awareness Yes (Keys on Workload Owner) No (Raw Pod Names) Aggregated metrics only
Cluster Footprint Zero (Client CLI only) Zero (Client CLI only) Heavy (Agents, CRDs, Storage)
Synthetic HTTP Probing Built-in (stdlib urllib) None Separate probe stack

Honest Limitations

  • Read-Only Scope: wasitme inspects Kubernetes object status and events; it does not parse container application logs or kernel eBPF probes.
  • Rollout Settling: Active rollouts should use --wait or --rollout to allow pods to settle before capturing the post-deploy state.
  • Platform: Linux and macOS (Python 3.11+). Windows is unsupported in v0.1.0.
